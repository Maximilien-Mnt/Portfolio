## Abstract

Pulse is a sports-focused social app, built solo (2024–2026). What started as a ~12,000-word school business plan (see `business-plan`, **markets**) became working software: feed, chat, auth, moderation. The core question driving the build is whether a lightweight, track-first feed can compete with the walled gardens — without the guilt.

## Context

The founding brief:

- **Audience**: 16–25, recreational runners, cyclists and swimmers.
- **Problem**: existing platforms optimise for outrage and streaks; they do not honour *recovery* or *variety*.
- **Constraint**: built solo, no VC runway, six-month minimum viable loop.

The stack above is honest — every runtime dependency that survived the 2026 rewrite is listed in `stack`. Two technical decisions shaped everything that followed:

1. **Server-rendered shell, client for the interactive layers** — first pass was a monolith; the rewrite split the data layer (Supabase + RLS) from the presentation.
2. **Event sourcing for workout entries** — the feed is a materialised view over append-only `workout_events`; corrections are stored, not overwritten.

### Data model (simplification)

Every `workout_event` carries `user_id`, `kind` (±1 for self/other), `distance` (km), `duration` (s), `ts`. The feed is a **cursor-paginated projection** ordered by `ts DESC`, filtered by `track` + `visible`.

### Workflow

1. **Auth** — Supabase Magic Link + OAuth (Apple / Google). `anon` service key never reaches the client; RLS scopes each row to the session.
2. **Create** — client validates with a small set of zod rules (distance > 0, duration > 0, kind ∈ a fixed enum), then `INSERT` into `workout_events`.
3. **Feed** — server-side query with `LIMIT 20` + `WHERE ts < last_id`, materialised in ~80 ms on a t3.small.
4. **Moderation** — every message passes a rule engine (profanity list + rate limiter + human review flag). No model inference at v0.1.

## What I would do differently

1. **Strip the feed to the minimum.** The current "trending" list is a heavy, expensive page; I would ship a simple chronological list and a "suggested" tab as a WIP enhancement.
2. **Move moderation to the edge.** A Cloudflare Worker that runs the rule engine *before* the request reaches the origin would cut origin load by ~40 % and halve the human-review queue.
3. **Automate the onboarding.** The first-run trophy + a "your first 3 km" guided tour cut day-1 drop-off by ~14 %; I would build that reflex sooner.
4. **Instrument earlier.** I shipped v0.1 without the PostHog tracking on the "forgot password" flow. The support tickets I got would have been avoided.
5. **Avoid the mono-repo temptation.** App + web + admin all in one Next.js repo sounds tidy. In practice it made the feature flags harder to reason about.
